# PRD（含权限）

把①业务建模的 9 块业务事实，转成一组可验收、可开发的需求规格：功能需求(FR)、验收标准(AC)、API规格、角色权限(RP)、页面权限(PP)。产出是 5 个内容块，彼此有明确上下游——FR 是网关，AC 和 API 并行消费 FR，权限链 RP→PP 串行。

**核心能力**：FR→[AC+API并行]→RP→PP。完整方法论见 `.scratch/hifi-workflow-skills/spec.md` §0.10。

本 skill 只管**需求规格化**：定义"做什么、怎么验收、什么接口、谁有权限"，不涉及页面怎么设计、数据怎么存。一旦话题滑向布局或数据表，停下来——那是③④的事。

## FR 映射：从 UC 到功能需求

> ②-11 的核心：怎么从①的 UC（业务用例）拆出 FR（功能需求）。

### 映射规则

- **1 个 UC → 1 个或多个 FR**：agent 拆分 + 人确认
- **拆分维度**（agent 按以下三轴拆）：
  - 参与角色（UC 里"谁做什么"的不同角色 → 各一个 FR）
  - 数据对象（UC 操作的不同实体 → 各一个 FR）
  - 操作类型（CRUD 拆分：查看/创建/编辑/删除 → 各一个 FR）
- **FR-UC 编号对应**：每个 FR 标注来源 UC（如 `FR-03 ← UC-02`），可追溯
- **版本过滤**：按①的 FL 版本计划，只产出本版本功能的 FR
- **SM 约束注入**：FR 涉及状态的，引用① SM 定义（如"状态=待审核"），不重新定义

### 映射示例

```
UC-02：管理员创建福利活动

agent 拆分 →
  FR-05：管理员创建活动（表单提交）           ← UC-02，操作=创建
  FR-06：活动基本信息校验（字段约束）          ← UC-02，操作=创建
  FR-07：活动金额超过5000触发审核              ← UC-02，操作=创建，引用SM
```

### 采集流程

```
① UC 列表（已确认）
    ↓ agent 按角色/对象/操作拆分
    ↓ 生成 FR 候选（含 FR-UC 对应）
    ↓ 按版本过滤（FL 版本计划）
    ↓ SM 约束注入（涉及状态的 FR）
    ↓ 人确认（确认/修正/否决 FR 条目）
FR 条目（状态=已确认）
```

## AC 派生：从 FR 到验收标准

> ②-12：每个 FR → 至少 1 个 AC，Given/When/Then 格式。agent 拆 + 人确认。

### 派生规则

- **每个 FR → 至少 1 个 AC**（上限按 FR 复杂度，agent 自动评估）
- **Given = FR 前置条件 / When = FR 触发动作 / Then = FR 结果**
- agent 从 FR 提取三要素 + 人确认
- 每个 AC 必须可直接测试（源文档 §3 的 2.1 注意点2）
- 声明版本和功能 ID

### 派生示例

```
FR-05：管理员创建活动（表单提交）
    ↓
AC-05-1：
  Given 管理员已登录后台
  When 填写活动信息并提交
  Then 活动创建成功，状态为"草稿"，记录创建者 ID
    ↓
AC-05-2：
  Given 管理员已登录后台
  When 金额 > 5000 且提交
  Then 触发财务审核，状态为"待审核"
```

### AC 与加工层同构

AC 的 Given/When/Then 格式与 ① 加工层同构——打通"规则→验收"链路：
- ① 加工层 Given/When/Then → ⑦ 汇报（客户确认规则）
- ② AC Given/When/Then → BDD → 测试用例（验收代码）

## API 端点推导

> ②-13：从 FR → Swagger/OpenAPI 端点。**人工设计**（涉及系统架构决策——agent 辅助推导但不替代）。

### 推导规则

- 每个 FR → 对应 CRUD 端点（agent 辅助推导，人决策端点聚合/拆分）
- Swagger/OpenAPI 格式硬约束（源文档 §3 的 2.1 注意点7）
- 每个端点含：method / path / request body / response / 错误码
- 与 SM 状态一致性校验（API 实现必须与 SM 定义的转换条件一致）

### 推导辅助

agent 从 FR 提取线索：
- FR 的 CRUD 类型（创建→POST、查看→GET、编辑→PUT/PATCH、删除→DELETE）
- FR 涉及的数据对象→路径中的资源名
- FR 的权限约束→端点的 auth 要求

### 人工决策点

- 端点聚合（多个 FR 共享一个端点？还是各自独立？）
- 分页/搜索/排序策略
- 错误码设计

## 权限链：RP → PP（②内部闭合）

> ②-14：权限概念在②内部闭合——①BRO→RP→PP，agent映射+人确认。

### RP 角色权限（角色→能力）

- **输入**：① BRO（业务角色：谁/什么角色/什么职责）+ AC 的 Given/Then
- **agent 从 AC 的 Given 提取角色约束**（谁触发），从 Then 提取角色能力（能做什么）
- **映射**：actor → role → 业务能力

**示例**：
```
① BRO：审核员 → 有审核权限的运营人员
AC-05-2 Given 管理员已登录 When 金额>5000 Then 触发审核
        → RP：管理员 → REVIEWER → 可创建需审核的活动
```

### PP 页面权限（角色→页面）

- **输入**：RP
- **agent 从 RP 的角色能力推导**可访问页面/路由
- **映射**：role → 可访问页面列表

### 分工

| 块 | 定义 | 例 |
|----|------|-----|
| RP role-permissions | "谁有什么业务能力" | 审核员 → 可审核活动 |
| PP page-permissions | "谁能访问什么页面" | 审核员 → /review 页面 |

## 5 块的生成顺序

```
① MRD（UC + SM + BRO）
    ↓
FR（网关：从 UC 映射）
    ↓
┌──────────┬──────────┐
AC（从 FR 派生）  API（从 FR 推导）
└──────────┴──────────┘
    ↓
RP（从 AC + BRO 推导）
    ↓
PP（从 RP 推导）
```

- **FR 先行**：所有块的上游，是 PRD 的网关
- **AC 与 API 并行**：互不依赖，都消费 FR
- **RP→PP 串行**：权限链，BRO→RP→PP 在②内部闭合
- 自动化程度：FR/AC/RP/PP agent 推 + 人确认；API 人工设计


## 项目适配

本 skill 通用，不绑特定项目。以下可按项目调整：

- **目录路径**：产物的存放位置由使用者项目结构决定（推荐默认见各块说明）

- **推荐默认**：输出格式和载体默认可改——见各块最佳形态说明
