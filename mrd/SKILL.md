# 业务建模

把"做一个 X 产品"这类模糊想法，钉成一组互相咬合、可逐块评审的业务事实：谁参与、对哪些对象、做什么、流程怎么走完、受什么规则约束、有哪些状态、最终拆成哪些功能。产出是 9 个内容块，彼此有明确的上下游咬合——上游改了，下游必须跟着回放。

**核心能力：规则整理（两层 pipeline）**。完整方法论见 `.scratch/mrd-rule-extraction/spec.md`。

```
输入文本 → [采集] → 原始层规则 [进 MRD，保真]    ← 规则唯一真相
                      ↓ [清洗]
                  加工层 Given/When/Then [进 ⑦ 汇报，清晰]
                      ↓
                  多次输入 → [增量沉淀] → 规则逐步成长
```

本 skill 只管**业务层**——角色/实体/流程/规则/状态/用例/旅程/愿景/功能。一旦话题滑向 UI 或实现，停下来——那是下游 skill 的事。

## 入口纪律

**意图不清或方案不清晰时，先梳理再走流程**：
- 需求模糊、业务逻辑不清 → 调用 `grill-with-docs` 盘问梳理
- 问题太大、路径不明 → 调用 `wayfinder` 建图寻路
- 梳理清楚后，回到本 skill 走流程

**misroute scan**（首次消息时检查）：如果用户的意图指向别的 jf-* skill，建议切换再继续。

## 规则本体

> 原始层条目 6 字段（规则ID/[原话]/[解读]/标签/来源/状态）+ 标签体系 + 来源追溯 + 状态生命周期。
> 完整定义见 `references/rule-schema.md`。核心：原话保真、解读标注、来源必带。

## 采集流程：从文本提取规则

> ②-02：agent 扫描输入文本→识别规则性陈述→提取候选规则条目。

### 输入来源

本 skill 不负责原始噪声过滤（那是上游 skill 的事）。到本 skill 时输入已是**干净文本**：

| 路径 | 来源 | 形态 |
|------|------|------|
| 主路 | imness（IM/会议妙记）/ docness（文档）/ 调研 skill | 干净结论文本 |
| 辅路 | 用户直接给的裸输入 | 待处理文本 |

### 采集步骤

```
上游文本（任意来源）
    ↓ Step1: agent 扫描，识别"规则性陈述"
      信号词：必须 / 不允许 / 超过 / 需要审核 / 只有...才能 / 自动 / 不得超过
    ↓ Step2: agent 提取候选规则条目
      每条含：[原话] + [解读] + 标签 + 来源，状态=候选
    ↓ Step3: 用户确认/补充/否决
      确认原话、采纳或修正解读、补标签
原始层规则条目 [状态=已确认]
```

### 采集纪律

- **[解读]标注**：agent 当场解读，明确标 `[解读]` 与 `[原话]` 区分。解读需用户确认才转正
- **来源必填**：采集时必须标来源（会议日期/章程条款号/竞品推断），无来源不收录
- **自由标签随手打**：整理时打 #实体 #场景 #优先级 标签，后期可归纳

## 加工层清洗：原始层 → Given/When/Then

> ②-03：把已确认的原始层[解读]清洗成 Given/When/Then 决策单元（进⑦汇报）。

### 清洗步骤

```
原始层条目（状态=已确认的 [解读]）
    ↓ 去重：多条解读指向同一约束的，合并
    ↓ 消歧：模糊表述精确化（"金额大的"→"金额>5000"）
    ↓ 结构化：解读 → Given/When/Then
    ↓ 关联：保留指向原始层规则ID 的追溯
加工层决策单元
```

### 清洗纪律

- **只清洗已确认的解读**，候选态不清洗
- **Given/When/Then 的每个要素都要能追溯到原始层规则ID**
- **清洗产物（加工层）进汇报材料，不回写 MRD**——MRD 只有原始层

### 清洗示例

```
原始层 BR-07：
  [原话] "金额大的活动要走财务审"
  [解读] "营销活动金额>5000 需财务审核"  ← 已确认

清洗成加工层：
  Given 活动类型为"营销"
  When 创建金额 > 5000 元
  Then 需财务审核，状态置为"待审核"
  追溯：BR-07
```

### 加工层与 AC 同构

加工层 Given/When/Then 与验证层 AC 范式一致——打通"规则→验收"链路：

```
加工层 Given/When/Then → ⑦ 汇报（客户确认）
                              ↓
                      验证层 AC → BDD 场景
```

## 增量沉淀与 SM 聚合

> 多次输入合并（新增/细化/疑似冲突）、agent 标冲突+人工裁决、SM 从加工层聚合。
> 完整流程见 `references/merge-and-sm.md`。
> 核心纪律：只标不裁、即时非批量、旧规则留痕。SM 不是独立产物——是加工层"涉及状态变更"子集的聚合视图。

## 9 个内容块

每块只写：上游 / 输出 / 质量门禁。块之间靠编号引用，不靠文件路径。

- **PV 产品愿景** — 上游：外部需求（市场/竞品/一句话想法）。输出：定位 + 目标用户 + 核心价值。门禁：必须含**量化 success-metrics + 反指标**（如"30 天转化率 +15%"+"退货率 ≤5%"），不可只有定性目标。无反指标的 PV 不放行。
- **BRO 业务角色** — 上游：PV。输出：参与业务的全部角色（人/组织），每个含职责。门禁：角色是下游权限的唯一来源，角色清单必须能回答"每个流程谁负责"。遗漏一个执行角色即不通过。
- **BEN 业务实体** — 上游：PV。输出：业务涉及的对象（活动/订单/券…）+ 实体关系。门禁：必须画出实体关系，是下游数据模型的唯一来源。
- **CP 核心流程** — 上游：BRO + BEN。输出：业务视角端到端流程（如 创建→审核→发布→领取→核销）。门禁：必须覆盖**所有角色的主流程**，是业务视角不是用户视角（CP 讲"事情怎么流转"）。
- **UC 业务用例** — 上游：CP。输出：每个流程节点拆成"谁做什么"的一句话用例，带 **UC 编号**（UC-01…）。门禁：必须是客户听得懂的业务语言，不出现技术词；每个 UC 可追溯到某个 CP 节点。
- **JF 用户旅程** — 上游：UC。输出：把用例拆成用户操作步骤的主路径。门禁：每条旅程**只写一条主路径**，分支用注释标注；区分 JF（人怎么走）与 CP（事怎么流转），二者不可混写。
- **BR 业务规则** — 上游：PV + 外部约束。输出：原始层规则条目（按本文件「规则本体」schema 组织）。门禁：每条含完整 6 字段；标签覆盖 ≥1 个预定义主分类；来源必带；禁止出现页面/组件/UI 细节。
- **SM 状态机** — 上游：BR（从规则中识别状态转换子集）。输出：状态定义 + 每状态含金额/权限/转换触发条件。门禁：SM 是**所有下游文档的唯一权威来源**，PRD 只能引用不能重定义；每个状态要素可追溯到 BR 条目ID。**BR 与 SM 交织涌现**——整理时一起冒出来，非先行 BR 再线性推导。
- **FL 功能清单** — 上游：PV。输出：功能列表（ID/名称/描述/优先级/模块）+ 版本规划（MVP/V1…→功能子集）+ **delta-description**（每版本相对上版的增量，非全量重写）。门禁：MVP 必须自洽可独立演示并覆盖 CP 主流程；版本间增减可追溯到功能 ID。

## 生成顺序（参考依赖，不是状态机）

9 块不是线性流水，是两支汇流。先生成时对照此图找上游；上游没就绪别硬写下游。

```
PV ──→ FL
  │
  ↓
BRO ┐
BEN ┤──→ CP ──→ UC ──→ JF
     │      ↑
BR ──┘──→ SM
```

- **两支**：BRO+BEN+BR 是"业务定义支"（谁/什么/什么规则）；PV 是"产品定位支"
- **CP 汇聚两支**（谁+什么+规则 → 流程）
- **DAG 已降级**：生成顺序是参考知识、不是状态机。状态追踪用 front matter commit + todo + 人驱动门禁

## 项目适配

本 skill 通用，不绑特定项目。以下可按项目调整：

- **目录路径**：产物的存放位置由使用者项目结构决定（推荐默认见各块说明）

- **推荐默认**：输出格式和载体默认可改——见各块最佳形态说明
