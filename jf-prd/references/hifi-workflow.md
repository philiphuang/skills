## 0. 宗旨：需求成长方案（两条暗线）

> 这套方法论不是"一次性把需求确认完再开发"，而是**需求成长方案**——需求像生物一样生长，在客户确认和研发细化之间往返迭代，逐步成熟。所有 skill 的存在都服务于这个成长过程。

### 0.1 两条暗线

整个方案由两条并行但目的不同的暗线驱动。**客户暗线**面向客户确认，**研发暗线**面向研发落实。它们在 ⑦ 阶段汇报处交汇。

```
   【客户暗线：面向客户确认】              【研发暗线：面向研发落实】
        ↓                                    ↓
   ① 业务建模（MRD）                   ②③④⑤⑥ + BDD
   逐步收集需求、理清客户规则           PRD/IA/线框/生成/BDD 细化需求
        ↓                                    ↓
   ⑦ 阶段汇报 ←──────────────────────── 研发产出 → 形成汇报素材
   跟客户确认设计结果                              ↓
   （屏蔽设计细节，聚焦决策）                  形成研发规则
        ↓                                    ↓
   客户反馈/变更                        保证需求落实和交付
        ↓
   回流 MRD（唯一入口）
```

### 0.2 客户暗线的设计哲学

| 原则 | 体现 |
|------|------|
| **MRD 是需求的唯一入口** | 客户的需求、规则、变更都先沉淀到 ① 业务建模（MRD），不在别处散落 |
| **汇报屏蔽设计细节** | ⑦ 阶段汇报站在客户视角，把业务流程/规则/界面**显性化抽离**——避免 PRD/IA 的工程细节淹没客户注意力 |
| **需求不是一次过** | 客户的需求存在多次变更（增/删/改）。方法论必须适应，不是假设一次确认完 |
| **规则 vs 设计分离确认** | **MRD 确认规则**（业务真相），**汇报确认设计结果**（阶段性成果）。两者评审对象不同，不混在一起 |

### 0.3 变更适应机制：变更只走 MRD

需求变更是常态，不是异常。方法论通过**单一入口 + 自上而下同步**保证变更不乱：

```
客户提出变更（新增/调整/删除）
        ↓
   只能进入 ① 业务建模（MRD）  ← 唯一入口，禁止在下游直接改
        ↓
   MRD 修订规则
        ↓
   沿生成关系自上而下同步（§2.1 修改纪律）
   ②PRD → ③页面架构/④数据建模 → ⑤线框 → ⑥生成
        ↓
   下次 ⑦ 阶段汇报反映新规则
        ↓
   客户再次确认 → 可能再变更 → 回流 MRD ...
```

**关键纪律**：
- **变更不直接改下游**（PRD/IA/线框）。发现下游要变，回溯到 MRD 改源头，再向下同步。
- **MRD 是规则唯一真相**。状态机、业务规则、金额审批边界只在 MRD 定义，下游只能引用。
- 这就是源文档 §2.1"自上而下修复"和 §1.5 DAG 的本质——它们不是技术规定，而是**变更治理哲学**的落地。

### 0.4 两条暗线如何映射到 skill

| 暗线 | skill | 职责 |
|------|-------|------|
| **客户暗线** | ① 业务建模 | MRD：**规则整理**（核心能力，两层 pipeline 详见 [MRD 方法论](mrd-rule-extraction/spec.md)）——原始层保真进 MRD 作规则唯一真相；加工层 Given/When/Then 进汇报 |
| | ⑦ 阶段汇报 | **提取显性化**（核心能力，详见 [⑦ 方法论](stage-report/spec.md)）——cherry pick 客户关心项转固定形态；两评审+一结论；反馈回流 MRD |
| **研发暗线** | ② PRD（含权限） | 需求规格化（FR/AC/API） |
| | ③ 页面架构 | 页面骨架/导航 |
| | ④ 数据建模 | 数据模型（独立链，源头在业务层） |
| | ⑤ 页面线框（含组件） | 视觉骨架 |
| | ⑥ 提示词与生成 | 翻译成可演示产物 |
| | BDD 工作法（套件外） | 汇报通过后做验收 |

**交汇点**：⑦ 阶段汇报。研发暗线的产出（②-⑥）cherry pick 成汇报素材喂给客户暗线；客户暗线的确认/变更回流到 ①。两条暗线在此往返，需求逐步成长。

### 0.5 ① 业务建模的核心能力：规则整理（两层 pipeline）

① 业务建模 skill 的核心功能是**规则整理**——把散乱输入沉淀成结构化业务规则（BR+SM），作为研发暗线的唯一真相来源。完整方法论见 [`mrd-rule-extraction/spec.md`](mrd-rule-extraction/spec.md)，这里是要点摘要：

```
输入文本 → [采集] → 原始层规则 [进 MRD，保真]    ← 规则唯一真相
                      ↓ [清洗]
                  加工层 Given/When/Then [进 ⑦ 汇报，清晰]
                      ↓
                  多次输入 → [增量沉淀] → 规则逐步成长
```

| 层 | 形态 | 去向 | 职责 |
|----|------|------|------|
| **原始层** | 自然语言 + 标签 + 来源 | MRD | 保真（客户原话/章程原条），可追溯，规则唯一真相 |
| **加工层** | Given/When/Then 决策单元 | ⑦ 汇报 | 清晰，客户确认，推导 SM |

**关键设计**：
- **MRD 保真，汇报清晰**——原始层进 MRD（保原貌），加工层进汇报（清洗成决策单元）
- **BR/SM 交织涌现**——SM 是原始层规则中"涉及状态变更"子集的聚合视图，非线性派生
- **加工层 Given/When/Then 同 AC 范式**——打通"MRD 规则 → 验证层 AC"链路
- **增量沉淀**：agent 标疑似冲突 + 人工裁决 + 状态流转留痕（候选→已确认→已入MRD→修订/废止）
- **输入由上游 skill 预处理**：imness（IM/会议）/ docness（文档）/ 调研 skill 产出干净文本，本方法论只管从文本采集规则

### 0.6 ⑦ 阶段汇报的核心能力：提取显性化 + 反馈回流

⑦ 阶段汇报 skill 的核心功能是**翻译**——把工程产物里客户关心的部分，翻译成客户能看懂、能确认的形态。完整方法论见 [`stage-report/spec.md`](stage-report/spec.md)，这里是要点摘要：

**核心思路：从"屏蔽"到"提取显性化"**——不是"砍掉工程细节怕淹没客户"（防御），而是"提取客户关心的，显性化成易消化形态"（积极）。

**阶段模型：两评审 + 一结论**：
```
业务评审（确认逻辑对不对）→ 设计评审（确认长什么样）→ 开发授权（结论）
```
开发授权是前两阶段通过的结论，非并列第三种文档。

**客户关心清单 12 项**（每项固定最佳形态）：
- 看得见（界面层）：界面高保真/文案/用户旅程
- 想得通（逻辑层）：use case/业务流程/用户状态/业务规则/页面布局/页面权限/外部对接/业务逻辑架构/系统分层架构
- 客户=业务客户为主，架构类是"超出认知的缓冲"（主动提供建信心）

**反馈回流闭环**：评审反馈=新的规则输入，复用 MRD 原始层格式，四类分流（疑问/否决/新增/调整），⑦ 采集反馈→① MRD 处理变更。需求在 ①→⑦→客户→① 间往返迭代成长。

### 0.7 ⑥ 提示词与生成的核心能力：两套独立生成路径

⑥ 的核心是**两套独立生成路径**，驱动方式根本不同：

| 路径 | 驱动 | 上游 | 目的 |
|------|------|------|------|
| **低保真** | 上游文档直接生成（**跳过提示词层**） | PRD + IA | 快速确认大框架大方向 |
| **准高保真** | 每页**自包含元提示词**驱动 | PRD+IA + ⑤线框 + 营销文案 + 设计体系 | 给 ⑦ 设计评审 |

**准高保真元提示词的核心逻辑**：每个页面一个专用元提示词，**自包含生成该页面所需的全部信息**——生成器读一个文件就能产出完整准高保真页面。
- 元提示词 = PC（覆盖）+ PB（禁止）合称，多节结构
- **Token/视觉写死值**（从设计体系拷贝进元提示词，生成时不依赖设计体系）
- **文案/数据引用**独立块（营销文案 CS / 演示数据集 DD，便于修改）
- **两步生成**：① 结构+视觉（长什么样）→ ② 文案+数据（说什么/显示什么）
- ⑥ 内部评审（视觉/文案/数据三项）通过后才交给 ⑦

**新增内容块：营销文案（CS）**——独立定义每页营销文案（中英文），元提示词引用它，⑦ 从它抽文案确认表。结构文案归 ⑤（客户不确认）。

### 0.8 ⑤ 页面线框的核心能力：EC 先行 + PW 自包含 + 状态驱动

⑤ 的完整内部机制（基于调研 + #55/#56/#54）：

**8 块生成顺序**：
```
①用户旅程 + ③页面架构 + ②PRD
    ↓
Step 1: EC 情绪曲线（先于 PW，双重角色：驱动设计 + 进⑦汇报）
    ↓ 驱动：页面优先级 / 状态重点 / 视觉文案重点
Step 2: PW 页面线框（含交互标注：导航/字段约束/状态触发，从 NM+IA 单页投影）
    ↓
Step 3: SV/MS/DDR 并行（三块都消费 PW，互不依赖）
    ├─ SV 状态变体（重点状态细画，被 EC 驱动）
    ├─ MS 弹窗规格
    └─ DDR 演示数据需求
    ↓
Step 4: GC 全局组件（从 PW 抽取，Rule of Three：≥3页重复）
    ↓ 组件与页面往复看（防过早抽象）
Step 5: CSM 组件状态矩阵（GC × 用户状态 笛卡尔积）
```

**关键设计**：
- **EC 先行**（⑤ 独创）：先生成情绪曲线驱动设计侧重（业界不在线框阶段做）
- **PW 自包含**（补业界空白）：线框自带交互标注，单看可评审，不依赖元提示词
- **EC 双重角色**：既是设计输入（驱动），又进⑦汇报（展示用户关怀）
- **组件往复**：GC 不提前抽象，从 PW 抽取后与页面往复看（Atomic Design 原则）
- **交互标注三要素**：导航（去哪）/ 字段约束（限制）/ 状态触发（何时可见）

### 0.9 ⑦ 清单补充：情绪曲线

⑦ 汇报客户关心清单（stage-report/spec.md §1）补充 EC：情绪曲线图（①旅程→⑤EC），展示"用户在每个触点的感受"——增强客户信心，呼应⑦"超出认知的缓冲"理念。

### 0.10 ②③④ PRD/页面架构/数据建模的核心能力

**② PRD（含权限）**：FR→[AC+API并行]→RP→PP。FR/AC/RP/PP agent推导+人确认；API人工设计（涉及系统架构决策）。权限链（①BRO→RP→PP）在②内部闭合。

**③ 页面架构**：PS→LT→NM→FA 全串行，全agent推导+人确认（mapping型）。NM是⑤PW交互标注的源头（单页投影）。

**④ 数据建模**：DC→CDF→TFD 全串行，独立链（消费①CP+BEN，**绕开②PRD**）。全agent推导+人确认。③和④并行（消费不同上游）。

## 3. 拆分原则

蓝图把 36 个内容块切成 8 个 skill（套件内 7 + 套件外 1），依据两条判据：

### 判据一：同构度 > 块数（#30）

一个 skill 装多少块不是关键，**块之间是否同构**才是。9 个同构块（如业务建模全是"上游/输出/门禁"三段式）很舒适；异质簇合并则割裂。判据来自业务建模 prototype——9 块草稿仅 55 行主体，在 Matt Pocock skill 舒适区内（参照 domain-modeling 75 行 / wayfinder ~110 行）。

### 判据二：生成关系断裂必拆（#31）

两个簇若在 DAG 里**零生成边相连**，各自有独立源头，必须拆成不同 skill。典型：数据三段（DC/CDF/TFD）源头是业务层 CP+BEN，与 PRD 的 FR/AC、与页面架构的 PS/LT/NM 都没有生成边——所以它独立。

### 轴线选择：为何是 C 混合（#33）

- **A 纵向（按四层）证伪**：2.0 设计层 25 块占全流程 70%，单个 skill 严重过载；1.0/3.0 又太轻。
- **B 切片（按端到端能力）**：在 IA 处数据/结构撕裂，本质同 C。
- **C 混合（按同构度+生成关系）**：粗参考源文档步骤，但同构簇优先聚合、断裂簇必拆，不强制对齐章节边界。

> **⑦ 阶段汇报**：纯组装，不创造新内容。从已有产出 cherry pick，站在用户视角把业务流程/规则/IA/导航/界面/权限**显性化抽离**成评审文档。**三阶段串行递进**（不是并行），每阶段基于当时已就绪的上游组装对应深度，上一阶段通过才进下一阶段：
>
> | 时序 | 阶段 | 评审材料产出 | 消费上游 | 通过后 |
> |------|------|------------|---------|--------|
> | 1 | 业务评审 | 业务流程图+角色+规则+状态机 | ① 业务建模 | 进入 2.0 设计层 |
> | 2 | 设计评审 | +功能架构+导航+低保真界面+权限 | +②③⑤ | 获演示确认，可启动 BDD |
> | 3 | 开发授权 | +AC 验收清单（PRD 派生） | +② AC | 获开发授权，进入 4.0 交付 |
>
> **发布能力**（配套）：评审材料产出后需发布给客户/干系人——HTML 发公网（Cloudflare/腾讯 Edge），MD 发飞书（`md2feishu` skill）。发布是 ⑦ 的内置环节，载体按评审场景选用。
>
> **BDD 时序**：BDD **在汇报通过后才开始**——设计评审(阶段2)通过后，BDD 基于PRD的AC + 客户反馈启动，做验收用例验收 4.0 的代码。BDD 不是 ⑦ 的输入，而是汇报下游的验收环节。
>
> **为何独立成 skill**：与前 6 个 skill（都"生产内容块"）职责正交——它是"组装汇报"，没有自己的生成逻辑。解决"MRD 不含设计、PRD 太冗余"：评审材料介于两者之间。**与 ⑥ 的分工**：⑥ 的 HTML/MD 评审评的是 ⑥ 自己生成的低保真产物；⑦ 评的是跨 skill 的阶段性成果。

## 6. 项目耦合插拔边界（#29）

skill 的每个 SKILL.md 分三层：**主体**（通用）/ **可选插件**（references/）/ **推荐默认**（可改）。

| 耦合点 | 处置 | 落位 |
|--------|------|------|
| BMAD/OpenSpec 映射 | 可选插件 | 每 skill 的 `references/sdd-mapping.md` |
| 飞书评审 | 全删 | 套件外独立 skill |
| stitch-shared-config | 可选插件 | 生成 skill 的 references |
| Figma MCP | 可选插件 | 生成 skill 的 references（视觉真相来源按项目配） |
| 具体目录路径 | 推荐默认可改 | skill 给建议结构，标注"可调整" |
| Token 三层架构 | 归套件外 | 设计体系 skill |
| 产物绑定 HTML | 默认可换 | 生成 skill 输出"指令+数据"，默认载体 HTML |
| 演示数据机制 | **保留核心** | 状态驱动设计是灵魂，不因通用化丢弃 |

**判断主线**：核心理念（状态驱动、自上而下、单一真相）不动；工具/平台（飞书/Figma/stitch/BMAD）全解耦为插件；目录/载体软化（推荐但不强制）。

## 7. DAG 机制降级说明（#28）

源文档的 DAG 模板/实例机制（`dag-template.json` + `dag-instance.json`，§2.11）整体**降级**：

| 项 | 处置 |
|----|------|
| dag-template.json / dag-instance.json 整套机制 | **删** |
| 自动/手动挡自动推进（auto_generate 级联） | **删**（skill 是能力不是流程引擎） |
| outdated 检测（upstream_status 快照） | **删**（用 git history + front matter commit 替代） |
| 生成顺序 + 引用约束（DAG 知识） | **留**——作方法论参考文档进 skill 正文 |
| 状态流转（pending→approved） | **替代**——用 todo + front matter commit + 人驱动门禁 |

核心理由：skill 是「被调用才运行」的能力，不是常驻流程引擎；agent 跨调用维持 JSON 状态不可靠；现有 skill 生态（triage 用 label、wayfinder 用 map+ticket、implement 用 CONTEXT.md）都不维护集中状态 JSON。详见 `research/dag-mechanism/findings.md`。
