## 2. jf-* skill 能力边界与触发信号词

> 顺序：**门面 → 拍内模块 → 基建**。门面判拍内，模块干活，基建跨拍。

### jf-mrd — 拍① 门面

| 属性 | 值 |
|------|---|
| 所属拍 | ① 业务事实 |
| 编排 | `jf-mrd-core`（1、4 步）→ `jf-review-core`（2 步）→ 人（3 步，现场） |
| 产出 | 出口 A：客户确认业务事实（MRD front-matter `status: 已确认`） |

**触发信号词（拍级，确信）**: 理清业务、MRD、需求整理、业务规则

**触发信号词（模糊→大概率）**: 我要整理业务需求、帮我把业务理清楚、这个系统要管什么、需求还没理清楚

| 下游 | ② `jf-prd`（读 ① 产物的 front-matter）；③ 的反馈按对象分流回本拍 |
|---|---|

**⚠️ 门面不新增判据**——只做「按序走 + 收退出码 + 卡住就停下问人」。

---

### jf-mrd-core — 业务建模本体（模块 ①）

| 属性 | 值 |
|------|---|
| 所属拍 | ①（由门面 `jf-mrd` 在第 1、4 步调用；显式指名时可独立调用） |
| 覆盖内容块 | PV, BRO, BEN, CP, UC, JF, BR, SM, DR (**9 块**) |
| 描述 | 把"做一个 X 产品"这类模糊想法，钉成一组互相咬合、可逐块评审的业务事实 |
| 核心能力 | 两层规则 pipeline: 原始层(真)→MRD, 加工层(Given/When/Then)→汇报 |
| 门禁 | `check_mrd.py` |

**触发信号词（确信）**: 规则整理、业务建模、业务角色、业务实体、核心流程、用例、状态机、决策记录、规则本体、两层 pipeline、增量沉淀、SM 聚合

**触发信号词（模糊→大概率）**: 先搞清楚业务、理清业务逻辑、梳理业务、产品思路

| 消费上游 | 无（① 是源头） |
| 下游 skill | ② `jf-prd`；③ 的答复回流 |
|---|---|

## 3. 边界模糊词归类建议

以下词**跨拍或跨模块**，单看字面定不下来。归类规则如下（`拍①/②/③` =
门面，其余为模块名）：

| 用户说的 | 可能指向 | 归类建议 | 仲裁策略 |
|----------|---------|---------|---------|
| **"需求"** | ① 业务需求（`jf-mrd-core`）<br>② 功能需求（`jf-prd-core`） | 看上下文——讨论"做什么业务"→①；讨论"功能怎么验收"→② | 默认 ①（源头）：需求先落到业务建模，业务清楚了再谈功能 |
| **"讨论/聊聊/想想/拿不准"** | `jf-interview`<br>① / ②（对象词指向） | 访谈意图词优先于对象词——"讨论一下这个需求"进 `jf-interview`，不进 ①/② | 已定型（8 件套过门禁且无待确认）→按对象词归类 |
| **"待确认/拍板/口径冲突"** | `jf-interview`（收敛待确认）<br>① `jf-mrd-core`（DR 决策记录） | 待确认清单与拍板归属 `jf-interview` 收敛；已拍板项不路由 | 无例外 |
| **"设计体系/风格/组件规范"** | `jf-design`（设计基线）<br>`jf-wireframe`（线框内组件） | 体系级（token/规范）→`jf-design`；线框内单个组件→`jf-wireframe` | 看粒度：跨页规范→`jf-design` |
| **"校验/检查/对不对"** | `jf-validate`（契约校验）<br>`jf-test`（测试验收） | 校验产物（manifest/原型）→`jf-validate`；写测试/BDD→`jf-test` | 测试→`jf-test`，其余→`jf-validate` |
| **"契约/manifest 字段"** | `jf-contract`（定义）<br>`jf-validate`（校验）<br>`jf-uxprompt`（渲染） | 问"什么意思/怎么写"→`jf-contract`；问"对不对"→`jf-validate`；"按它出页面"→`jf-uxprompt` | 要解释→`jf-contract`，要结论→`jf-validate`，要产出→`jf-uxprompt` |
| **"设计"** | ② `jf-prd-core`（API设计）<br>`jf-ia`（页面架构）<br>`jf-wireframe`（线框） | 看上下文——API/接口设计→②；页面结构/导航→`jf-ia`；线框/具体页面→`jf-wireframe` | 默认 `jf-ia`：设计=页面架构是高频意图 |
| **"页面"** | `jf-ia`（PS 页面结构）<br>`jf-wireframe`（PW 线框）<br>`jf-uxprompt`（生成） | 看阶段性——只问"有哪些页面"→`jf-ia`；画"页面具体怎么排"→`jf-wireframe`；"生成页面"→`jf-uxprompt` | 默认 `jf-ia`：先搞清楚页面结构，再画/再生成 |
| **"数据"** | ① `jf-mrd-core`（BEN 实体）<br>`jf-data`（DC 数据域 / TFD 表） | 看粒度——"有哪些实体"→①；"表怎么设计"→`jf-data` | 默认 ①（源头）：数据模型从业务实体来 |
| **"状态"** | ① `jf-mrd-core`（SM 状态机）<br>`jf-wireframe`（SV 状态变体） | 看范畴——"有哪些状态/怎么流转"→①；"每种状态下页面怎么显示"→`jf-wireframe` | 默认 ①（源头）：状态定义在 MRD，线框只能引用 |
| **"权限"** | ② `jf-prd-core`（RP 角色权限）<br>`jf-ia`（PP 页面权限） | 看对象——"谁能做什么操作"→②；"谁能访问什么页面"→`jf-ia` | 默认 ②（源头）：先有能力再有页面权限 |
| **"生成/写代码"** | `jf-uxprompt`（生成低保真）<br>非 jf-*（高保真代码） | 看阶段——低保真验证→`jf-uxprompt`；正式开发→非 jf-* | 看前置：②设计生产段未完成→`jf-uxprompt`；全部完成且门禁通过→非 jf-* |
| **"测试"** | `jf-test`（BDD+TC）<br>通用编码测试 | 看范畴——验收测试→`jf-test`；单元测试/集成测试→非 jf-* | 看是否有 AC：有 AC→`jf-test` |
| **"评审/汇报"** | ③ `jf-review`（有产出时）<br>① `jf-mrd`（业务评审，无产出时） | 看对象——客户/老板看设计→③；业务逻辑对不对→① | 无产出→拒绝，指向 ① |

## 4. 路由优先级规则

**router 判跨拍，门面判拍内。** 路由只回答「落在哪一拍」，进门面之后由门面按步骤表
找「第一个产物不存在 ∨ 门禁没过」的步骤。

### 4.1 定拍

```
① 业务事实（源头）
  ↓ 出口 A · MRD status: 已确认
② 需求与设计（设计生产段）
  ↓ 设计生产段出口
③ 客户评审
  ↓ 出口 B · 开发授权
② 需求与设计（交付研发段：jf-test）
  ↓
非 jf-*（通用开发）
```

**例外**: 访谈意图词（讨论/聊聊/拿不准/待确认/拍板/口径冲突）优先于对象词——
即使对象词指向更上游的拍，先进 `jf-interview`（它在 ②1）。

### 4.2 定落点

拍定下来之后，落点按用户有没有**显式指名**分：

| 情况 | 落点 |
|---|---|
| 用户显式指名的 skill **属于**这一拍 | 就是它自己（match）——模块可独立调用，行为与门面编排无关 |
| 用户显式指名的 skill **不属于**这一拍 | 切到这一拍的**门面**（mismatch）——门面再判拍内从第几步进 |
| 用户没指名（拍级触发词） | 这一拍的**门面** |

**拍级触发词以三个门面的 `description` 为准**（`jf-mrd`「理清业务 / MRD / 需求整理 / 业务规则」；
`jf-prd`「写 PRD / 功能需求 / 验收标准」；`jf-review`「阶段汇报 / 客户评审 / 需求确认 / 设计评审」）。
本文件是它的**分类视图**——改一处必须改两处。

### 4.3 拍内次序（门面自己用，router 只判断「是不是同一拍」）

```
jf-interview > jf-prd-core > jf-ia ≈ jf-data > jf-design > jf-wireframe > jf-uxprompt > jf-test
jf-mrd-core > （① 内没有别的生产模块）
```

（`jf-ia` 和 `jf-data` 并行，同时命中时优先 `jf-prd-core`，因为它是 `jf-ia` 的上游；
`jf-design` 在 IA 之后、线框之前，是两者的公共设计基线）

### 4.4 三个特殊

```
jf-review 特殊:
  有已有产出物 → 执行 ③
  没有 → 拒绝，指向 ①

jf-validate 特殊:
  基建门禁，各拍生成后必过；不替代 jf-test（测试仍走 ②交付研发段）

jf-contract 特殊:
  基建定义层，不推进流程、不产生产物；只回答「契约怎么写」。
  同一句里出现 manifest 时按意图分：要解释→jf-contract，要结论→jf-validate，
  要产出→jf-uxprompt，要清单→jf-ia
```

## 5. DAG 依赖映射（路由层用）

路由层不需要追踪块是否就绪，但需要知道"哪个 skill 是哪个的源头"来判定**跨拍**方向：

```
用户说 → 信号词匹配 → 目标拍 → 落点

① jf-mrd (源头，无上游)
  ├─→ jf-interview (消费 MRD 的 [待确认] + DR 待拍板项；访谈词命中时优先于此)
  ├─→ jf-prd-core  (消费 MRD 的 UC+SM+BRO)
  ├─→ jf-data  (消费 MRD 的 CP+BEN, 绕开 PRD)
  └─→ jf-review-core (消费 MRD 各块)

② jf-interview (消费 MRD)
  └─→ jf-prd-core  (G1–G7 门禁通过后移交；待确认沿 pages[].note 追溯)

② jf-prd-core (消费 MRD)
  ├─→ jf-ia  (消费 PRD 的 FR+AC)
  ├─→ jf-wireframe  (消费 PRD+IA+JF)
  └─→ jf-test  (消费 PRD 的 AC)

② jf-ia (消费 PRD)
  ├─→ jf-design  (IA 的页面清单是设计基线的作用面)
  └─→ jf-wireframe  (IA 的 PS+LT+NM 是 PW 的前置)

② jf-data (消费 MRD，与 IA 并行)
  └─→ (独立链，下游是非 jf-* 的 DB)

② jf-design (消费 IA)
  └─→ jf-wireframe, jf-uxprompt  (两者共用同一设计基线)

② jf-wireframe (消费 IA+PRD+JF)
  └─→ jf-uxprompt  (PW+CSM+NM 是元提示词前置)

② jf-uxprompt (消费 Wireframe+PRD+IA)
  ├─→ jf-validate  (生成后必过契约校验，不通过打回)
  └─→ jf-review-core (准高保真产物进 ③)

基建 jf-validate (消费 manifest + 渲染产物)
  └─→ jf-test / ③评审 (通过后放行)

基建 jf-contract (定义层，无上游 — 被引用，不被消费)
  └─→ jf-ia / jf-uxprompt / jf-validate  (三者都以 manifest-schema.md 为准)

③ jf-review-core (消费一切 → 答复按对象分流)
  └─→ ① jf-mrd-core (业务事实类) / ② (需求、设计类)

② jf-test (交付研发段，消费 PRD 的 AC + ③ 的客户反馈)
  └─→ (验收非 jf-* 的代码)
```
