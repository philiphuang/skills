# 阶段汇报

纯组装，不创造新内容。从各skill产出cherry pick客户关心的12项，翻译成易消化形态，按两阶段（业务评审→设计评审）组织汇报文档，收集反馈回流MRD。

核心思路：**提取显性化**（非屏蔽）——不是砍掉工程细节，而是主动挑出客户关心的、翻译成他们能看懂的形态。

## 入口纪律

**先走 jf-router 意图分类**：
1. 用 `products/jf-router/SKILL.md` 判断用户意图落在高保真工作法哪一层
2. 若目标 skill ≠ 本 skill → 终止本 skill 流程，输出路由结果并直接按目标 skill 执行
3. 若目标 skill = 本 skill → 继续本 skill 流程

**jf-review 特殊检查**：若当前无已产出的上游文档可 cherry pick，拒绝执行，提示从 jf-mrd 开始。

**意图不清或方案不清晰时**：
- 需求模糊、业务逻辑不清 → 调用 `grill-with-docs` 盘问梳理
- 问题太大、路径不明 → 调用 `wayfinder` 建图寻路
- 梳理清楚后回到本 skill，重新走 jf-router 分类

## 两阶段

```
业务评审（确认逻辑对不对）→ 设计评审（确认长什么样）→ 开发授权（结论）
```

开发授权是前两阶段的自然产出，非并列第三种文档。

## 设计注释文档（产物B）

**上面 12 项是给客户的，这一份是给内部的。** 同一批上游产出切两刀：客户材料讲
「这个产品长什么样、逻辑对不对」，产物B 讲「每一处为什么这么设计、依据在哪」。
两者**物理分开**——产物B 的内容不许出现在客户材料里，更不许出现在客户演示树里
（那棵树的纪律归 jf-uxprompt「演示档纪律」管）。

文件名 `<产品>-设计注释.md`，受众是 PM / 内部评审。

### 与 12 项清单的分工

| | 客户材料（12 项） | 产物B（本文件） |
|---|---|---|
| 受众 | 客户 | PM / 内部 |
| 形态 | 图 / 表 / 截图，翻译成客户读得懂的 | 追溯表，**保留**编号与来源 |
| FR/AC/BR 编号 | 不出现 | **必须有**——它是追溯的主键 |
| 判据 | 客户看得懂吗 | 每个结论指得回上游吗 |

jf-hifi 的产物B 模板有 7 节，其中四节**在别处已有落点，不重复登记**：§0 输入来源
就是 manifest 的追溯字段；§1 页面清单就是 `manifest.pages[]`（渲染器的输入，
不必手抄一份）；§3 逐屏拆解注释与 12 项的「页面布局思路」重合；§6 未拍板项已经是
jf-interview 的 open-questions 链。本 skill 真正新增的是**三张表**：

### §2 业务场景清单（带来源）

| 场景ID | 业务环节 | 页面 | 页面状态 | 关键组件状态集 | 来源 |
|---|---|---|---|---|---|
| S-01 | 立项-创建 | 立项申请 | 正常 | 表单可编辑、保存可用 | CP / FR |
| S-02 | 立项-列表 | 我的立项 | 空态 | 空状态组件 + 创建 CTA | UC / AC |
| S-03 | 立项-提交 | 立项申请 | 错误 | 金额字段行内报错 + 顶部提示 | BR / AC |

这张表是 `manifest.scenes[]` 的**文档形态**：`id` / `title` / `source` 逐字段对应，
`steps[]` 展开成「页面 + 页面状态」两列。**来源必填**——它是「这个组合业务上真的
会发生」的唯一证明。

**不是「每页 × 全状态」矩阵**：那是笛卡尔积遍历。业务上不存在的组合写不出 `source`，
所以它压根填不进这张表——jf-hifi 那条「场景 ≠ 笛卡尔积」的纪律，落到纸面上就是
这一列空格填不上。

### §4 组件主场景与边际场景表

| 组件 | 主场景状态 | 边际场景状态 | 出现在场景 |
|---|---|---|---|
| 金额输入 | 可编辑、格式提示 | 超限 → 行内错误 + 顶部提示 | S-01 / S-03 |
| 项目列表 | 多行数据 + 状态徽标 | 无数据 → 空状态组件 + CTA | S-01 / S-02 |
| 提交按钮 | 可点击 | 必填缺失 → 禁用 + 提示 | S-01 / S-03 |

组件**随业务场景成组出现**，不单独把每个组件轮流切成各状态——第三列就是这条的
落地：每个组件都指得回 §2 的场景 ID。

### §5 客户适配检查表

判定口诀（jf-hifi 原表，抄在这里免得两头漂移）：

- 客户能**看得到、点得到、读得懂**的 → 进客户材料
- 客户看了会**困惑、误解、追问实现**的 → 留在产物B
- 拿不准的 → **默认进产物B**，评审后再决定是否上浮

| 只进产物B 的内容 | 为什么不给 |
|---|---|
| FR / AC / BR 编号、规则来源、字段约束来源 | 内部追溯，客户不关心 |
| 页面 ID / 路由 / 布局类型（工程标注） | 工程视角 |
| 交互标注的书面说明（导航 / 字段约束 / 状态触发） | 设计决策依据 |
| 未拍板的决策 / 待定项 | 暴露不确定性，可能被误读为承诺 |
| 乙方成本 / 排期 / 风险 | 商业敏感——不进任何交付物 |
| 对旧系统 / 竞品的负面对比 | 易引发争议 |
| 后端未就绪的「伪功能」 | 客户误以为已实现；界面可用但须标「演示数据」 |
| 页面权限 / 技术架构 / API | 工程实现细节 |

### 交付前对拍

```bash
python3 products/jf-uxprompt/scripts/check_demo_separation.py <演示目录> \
    --manifest <项目>/manifest.json --notes <产品>-设计注释.md
```

B 侧查两件事：**B1** 产物B 存在、非空、是 `.md`；**B2** `manifest.scenes[]` 每条的
`id` / `title` / `source` 都出现在产物B 里。缺一条报 B2 不通过。

⚠️ **B2 只证明「场景逐条落进了文档」，不证明三张表写得好**——表格质量归人看。
它挡的是那类「写了一堆通用模板话、一条场景都没落地」的产物：那种文档过得了肉眼
扫读，过不了逐字段对拍。

## 标注气泡协议（设计评审现场用）

设计评审不是「把页面投屏让客户看一遍」，是**逐条过标注**。
`manifest.annotations` 就是评审索引——每条标注 = 一个要当着客户面确认的点，
已经按契约在页面上落了编号徽标（协议权威版本见
`products/jf-contract/references/manifest-schema.md#annotations`）。

### 评审前

1. 跑一遍渲染，**先把 stderr 的未落点 WARN 收下来**：

   ```bash
   python3 products/jf-uxprompt/scripts/render_manifest.py manifest.json 2> render.warn
   ```

2. 按页面分组取 `manifest.annotations`，每条即一个待过项，编号就是过场顺序。
3. `status: resolved` 的（上一轮已答复）不重复问；`rejected` 的必须重提——
   客户否决过的东西，改完要拿新版本回来确认。

### 现场

打开原型 → 点编号徽标 → 气泡弹出（标注 id / 状态 / target + title + content）
→ 逐条念给客户 → **当场记答复**：

- 客户说「可以」→ 记 `resolved`
- 客户说「不行 / 不要这个」→ 记 `rejected`，**并且必须带出到反馈记录**
- 客户说「再想想 / 要问别人」→ 留 `active`，进待确认清单

### 三态回写时机

| 值 | 含义 | 什么时候写 |
|---|---|---|
| `active` | 待确认（缺省） | 默认态；答复之前一直是它 |
| `resolved` | 已答复 | **当场**写——离场后补记的答复不算数 |
| `rejected` | 客户否决 | 当场写，且同一条必须出现在反馈记录里 |

三态只是**评审进度**，不是需求变更本身。写 `status` 不等于改了需求——
变更照旧走下面那条回流闭环（①MRD 是变更唯一入口）。

### 未落点标注必须显式带出

渲染器报 WARN 的那批标注（进了「评审标注 · 未落点」区的）**一条都不许跳**。
它们恰恰是最该问的：「批量审批按钮」这类元素在骨架里还不存在，正说明需求
本身还没落定；因为「页面上点不到」就跳过，等于把最不确定的部分藏了起来。

做法：把渲染的 WARN 原样带进汇报材料，单列一节「**页面上还没有对应元素的标注**」，
逐条问、逐条记答复——客户读到的仍是 title + content，与点了徽标等价。

### 反馈回流

气泡里记下的答复 → 复用 MRD 原始层格式（**原话 + 解读 + 来源 + 状态**）
→ 四类分流（疑问 / 否决 / 新增 / 调整）→ 回流 ①MRD（变更唯一入口）
→ MRD 修订 → 下游同步 → 下次汇报反映。

## 反馈回流闭环

```
客户评审 → 反馈（疑问/否决/新增/调整）
    ↓ 复用MRD格式记录
    ↓ 四类分流
    ↓ 回流①MRD（变更唯一入口）
    ↓ MRD修订 → 下游同步 → 下次汇报反映
```

- **⑦采集反馈，①处理变更**
- 反馈记录格式复用①原始层（原话+解读+来源+状态）

## 纪律

- **纯组装**：不创造新内容，从已有产出cherry pick
- **标注只消费不创造**：标注由上游（③IA 落 manifest、渲染层落点）产出，
  现场发现标注缺了或写错了，回上游补，不在这儿现编一条
- **未落点必带出**：渲染 WARN 的标注一条都不许跳（见上节）
- **答复不回写 `status` 等于没问**：三态当场写；离场后补记的答复不算数
- **提取非屏蔽**：挑客户关心的，主动翻译
- **产物B 不进客户材料**：设计注释是内部追溯文档，客户材料与客户演示树里都不许出现
  （编号、来源、页面 ID、未拍板项——客户按 Ctrl+U 也不该看到）。分离门禁：
  `check_demo_separation.py`
- **每项固定形态**：流程→流程图，状态→状态图，规则→决策表…
- **两评审+一结论串行**：业务评审(逻辑层)→设计评审(+界面+架构)→开发授权(结论)
- **通过≠零反馈**：允许带待定问题，否决类必须当场解决
- **发布**：HTML→公网，MD→飞书（md2feishu）。以上载体默认可换


## 项目适配

本 skill 通用，不绑特定项目。以下可按项目调整：

- **目录路径**：产物的存放位置由使用者项目结构决定（推荐默认见各块说明）
- **执行外包**：本 skill 是纯组装（cherry pick），不外包。上游各 skill 的执行可外包。
- **推荐默认**：输出格式和载体默认可改——见各块最佳形态说明
