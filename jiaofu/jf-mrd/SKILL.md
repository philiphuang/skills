# 业务建模

把"做一个 X 产品"这类模糊想法，钉成一组互相咬合、可逐块评审的业务事实：谁参与、对哪些对象、做什么、流程怎么走完、受什么规则约束、有哪些状态、哪些口径/决策已由业务方拍板。产出是 10 个内容块，彼此有明确的上下游咬合——上游改了，下游必须跟着回放。

**核心能力：规则整理（两层 pipeline）**。完整方法论见 `references/mrd-rule-extraction.md`。

```
输入文本 → [采集] → 原始层规则 [进 MRD，保真]    ← 规则唯一真相
                      ↓ [清洗]
                  加工层 Given/When/Then [决策就绪 → 进 MRD DR 块 / 或进 ⑦ 汇报，清晰]
                      ↓
                  多次输入 → [增量沉淀] → 规则逐步成长
```

本 skill 只管**业务层**——角色/实体/流程/规则/状态/用例/旅程/愿景/功能。一旦话题滑向 UI 或实现，停下来——那是下游 skill 的事。

## 入口纪律

**先走 jf-router 意图分类**：
1. 用 `products/jf-router/SKILL.md` 判断用户意图落在高保真工作法哪一层
2. 若目标 skill ≠ 本 skill → 终止本 skill 流程，输出路由结果并直接按目标 skill 执行
3. 若目标 skill = 本 skill → 继续本 skill 流程

**产出前先核对规则缺口**：

- 若项目仓库维护了评审批注/经验/变更记录，先加载其中涉及 jf-mrd 的部分；
- 以本文件门禁为准产出；发现「经验记录已提、本文件未覆盖」的缺口时，先在本文件落地再产出；
- 规则吸收的来源与历史记于 git 提交与关联 issue，不在本文件维护批注流水。

**意图不清或方案不清晰时**：
- 需求模糊、业务逻辑不清 → 调用 `grill-with-docs` 盘问梳理
- 问题太大、路径不明 → 调用 `wayfinder` 建图寻路
- 梳理清楚后回到本 skill，重新走 jf-router 分类

## MRD 头部 front-matter

每份 MRD 以 YAML front-matter 开头（`---` 包裹），头部元数据（业务方/版本/范围/上游输入/覆盖度/复用评估/关联）一律放 front-matter，**不用正文 bullet 块**。字段 schema 如下：

| 字段 | 必填 | 说明 |
|------|------|------|
| `title` | ✓ | 文档标题（文件名/需求名） |
| `business_owner` | ✓ | 业务方，格式「组织 · 角色」（角色见 BRO 门禁，人名不充当角色） |
| `version` | ✓ | 版本号 vX.Y |
| `status` | ✓ | 文档状态（待评审/已拍板/已确认…） |
| `updated` | ✓ | 最近更新日期 |
| `requires` | ✓ | 上游输入文件清单（会议纪要/逐字稿/需求清单/旧稿…），与 jf-prd `references/hifi-workflow.md` 的 `requires` 声明对齐 |
| `scope` | ✓ | 范围：需求清单序号/领域 + 一句话边界 |
| `coverage` | ✓ | 覆盖度：深度/批量 + 缺口标注 |
| `reuse_assessment` | ✓ | 复用评估：与既有系统/旧稿/平台层的复用或矛盾结论 |
| `related` | · | 关联 MRD/需求编号 |
| `changelog` | ✓ | 版本沿革列表（倒序：版本/日期/变化摘要） |

**门禁**：

- 头部必须是合法 YAML（list 字段用 `-` 子项），新写 MRD 不得回到正文 bullet 元数据块；
- `version` / `status` / `updated` / `changelog` 随每版更新，状态追踪走 front matter，不在正文重复；
- `requires` 缺失或与上游输入不符不放行（下游据此判断依赖就绪）。

```yaml
---
title: XX-MRD
business_owner: XX部 · 角色名（当前负责人：YY）
version: v0.1
status: 待评审
updated: YYYY-MM-DD
requires:
  - 会议纪要/xxx-纪要.md
scope: 需求清单序号 X（领域 > 模块）——一句话边界
coverage: ✅ 深度覆盖 xx；⚠️ 待提供 yy
reuse_assessment: 与既有 zz 的关系/复用结论
related:
  - 关联 MRD 编号
changelog:
  - v0.1：首次成稿
---
```

## MRD 文档大纲与编号规则

MRD 是业务层唯一真相文档，结构按业务层级**嵌套**组织：UC 是 CP 的子章节，JF 是 UC 的子章节，
BR/SM 是 JF 的子章节——不把 UC/JF/SM 拉成并列顶层章节。章节号随嵌套自然带出父链（`4.1 CP-01`
→ `4.1.1 UC-01` → `4.1.1.1 JF-01`），评审按层级扫读。

### 章节骨架

```text
front matter（字段见「MRD 头部 front-matter」）
# <模块名>-MRD
1. PV 产品愿景
2. BRO 业务角色
3. BEN 业务实体
4. CP 核心流程
   4.0 层级总览（需求 → CP → UC → JF → BR/SM，JF 标注所含 BR 与 SM）
   4.1 CP-01 <流程>（每条 CP 一张 flowchart）
       4.1.1 UC-01 <用例>（UC 是 CP 的子章节）
           4.1.1.1 JF-01 <旅程>（JF 是 UC 的子章节：标题带所属 CP·UC 与主导角色，如
             `JF-01 …（CP-01 › UC-02 ｜ 角色）`）
               主路径步骤
               业务规则（BR 是 JF 的子章节）
               业务状态切换（SM 是 JF 的子章节：涌现视图 + 该 SM 的权威定义收口）
       4.1.2 UC-02 <用例>（同 4.1.1）
   （一条 UC 可有多条 JF；一条 JF 服务多个 UC 时挂在主导 UC 下，其余 UC 交叉标注）
   4.2 CP-02 <流程>（同 4.1）
5. 需求级全局规则（跨 UC 的边界/范围/优先级/保密类 BR，挂需求层，单独小节收编）
6. DR 决策记录
7. 术语表
8. 信息来源清单
附 A. 待确认清单（单独列，不埋在正文）
```

### 编号规则

| 对象 | 编号格式 | 规则 |
|---|---|---|
| CP | CP-xx | 模块内核心流程顺序号；编号保持稳定，移动章节不重排 |
| UC | UC-xx | 编号书写与标题都带所属父链——条目写作 `CP-01 › UC-02`；块 ID `UC-02` 模块内全局连续，不随父链变化重号 |
| JF | JF-xx | 编号书写与标题都带所属父链——`JF-01 发起收集任务旅程（CP-01 › UC-02 ｜ 材料审核岗）`；块 ID `JF-01` 模块内全局连续，一条 JF 服务多个 UC 时列出全部或标注主导 UC |
| BR | BR-NN | 模块内全局连续；物理位置随 UC-JF 分散到 JF 子章节，编号不随位置重排 |
| SM | SM-xx | 模块内唯一权威号；涌现视图在所属 JF 内，权威定义收口于该 SM 的主导 JF（引用写 `CP › UC › JF › SM-xx`） |
| DR | D-xx | 决策记录顺序号 |
| 附 A | A.x | 待确认/决策登记序号 |

**层级从属的承载方式**：父-子关系用「章节嵌套（`4.1 CP-01 → 4.1.1 UC-01 → 4.1.1.1 JF-01`）+ 编号/标题父链 + 追溯列 + 层级总览图」表达。
**编号书写与标题都带所属父链**：UC/JF/BR/SM 在正文、图与跨节引用中一律书写完整父链（如 `CP-01 › UC-02 › JF-01`、`CP-01 › UC-02 › JF-01 › BR-03`），标题同样写 `JF-01 …（CP-01 › UC-02 ｜ 角色）`。
**块 ID 与重号纪律**：父链是书写/展示用的所属上下文，**不并入块 ID**——`CP-xx`/`UC-xx`/`JF-xx`/`BR-NN`/`SM-xx` 各自模块内全局连续，移动章节不重号。

## 规则本体

> 原始层条目 6 字段（规则ID/[原话]/[解读]/标签/来源/状态）+ 标签体系 + 来源追溯 + 状态生命周期。
> 完整定义见 `references/rule-schema.md`。核心：原话保真、解读标注、来源必带。

## 采集流程：从文本提取规则

> ②-02：agent 扫描输入文本→识别规则性陈述→提取候选规则条目。

### 输入来源

本 skill 不负责原始噪声过滤（那是上游 skill 的事）。到本 skill 时输入已是**干净文本**：

| 路径 | 来源 | 形态 |
|------|------|------|
| 主路 | imness（IM/会议妙记）/ docness（文档）/ 调研 skill | 干净结论文本 |
| 辅路 | 用户直接给的裸输入 | 待处理文本 |

### 采集步骤

```
上游文本（任意来源）
    ↓ Step1: agent 扫描，识别"规则性陈述"
      信号词：必须 / 不允许 / 超过 / 需要审核 / 只有...才能 / 自动 / 不得超过
    ↓ Step2: agent 提取候选规则条目
      每条含：[原话] + [解读] + 标签 + 来源，状态=候选
    ↓ Step3: 用户确认/补充/否决
      确认原话、采纳或修正解读、补标签
原始层规则条目 [状态=已确认]
```

### 采集纪律

- **[解读]标注**：agent 当场解读，明确标 `[解读]` 与 `[原话]` 区分。解读需用户确认才转正
- **来源必填**：采集时必须标来源（会议日期/章程条款号/竞品推断），无来源不收录
- **自由标签随手打**：整理时打 #实体 #场景 #优先级 标签，后期可归纳

## 加工层清洗：原始层 → Given/When/Then

> ②-03：把已确认的原始层[解读]清洗成 Given/When/Then 决策单元（进⑦汇报）。

### 清洗步骤

```
原始层条目（状态=已确认的 [解读]）
    ↓ 去重：多条解读指向同一约束的，合并
    ↓ 消歧：模糊表述精确化（"金额大的"→"金额>5000"）
    ↓ 结构化：解读 → Given/When/Then
    ↓ 关联：保留指向原始层规则ID 的追溯
加工层决策单元
```

### 清洗纪律

- **只清洗已确认的解读**，候选态不清洗
- **Given/When/Then 的每个要素都要能追溯到原始层规则ID**
- **决策就绪的清洗产物（加工层）可进 MRD 的 DR 决策记录块作为决策依据（保真原话），或进汇报材料**——决策内容回 MRD 供业务方拍板，汇报只是呈现；未拍板内容不回 MRD

### 清洗示例

```
原始层 BR-07：
  [原话] "金额大的活动要走财务审"
  [解读] "营销活动金额>5000 需财务审核"  ← 已确认

清洗成加工层：
  Given 活动类型为"营销"
  When 创建金额 > 5000 元
  Then 需财务审核，状态置为"待审核"
  追溯：BR-07
```

### 加工层与 AC 同构

加工层 Given/When/Then 与验证层 AC 范式一致——打通"规则→验收"链路：

```
加工层 Given/When/Then → ⑦ 汇报（客户确认）
                              ↓
                      验证层 AC → BDD 场景
```

## 增量沉淀与 SM 聚合

> 多次输入合并（新增/细化/疑似冲突）、agent 标冲突+人工裁决、SM 从加工层聚合。
> 完整流程见 `references/merge-and-sm.md`。
> 核心纪律：只标不裁、即时非批量、旧规则留痕。SM 不是独立产物——是加工层"涉及状态变更"子集的聚合视图。

## 10 个内容块

每块只写：上游 / 输出 / 质量门禁。块之间靠编号引用，不靠文件路径。

> FL 功能清单已移出 MRD——MRD 不放功能清单，FL 归 PRD；MRD 纯粹记录业务逻辑，不做分析。

**MRD 结构层级**：本 skill 产出须体现一条显式层级链（需求 → CP → UC → JF → BR/SM），
评审一眼看清咬合。层级表达规则见上文「MRD 文档大纲与编号规则」；落到各块的门禁见下列条目。

**mermaid 图示布局**：flowchart 节点数 >5 一律用 **TD（自上而下）**，不用 LR——横向超宽不可读；
2-3 节点的小关系图（如核心流程总关系图）可保留 LR。适用一切 mermaid flowchart：CP 流程图、
UC 串联图、层级总览图、SM 状态图。

**术语纪律**：MRD 引入新业务名词/实体名/规则简称前，先查平台层既有术语，避免撞名歧义；
已撞名的在首次出现处显式区分。

- **PV 产品愿景** — 上游：外部需求（市场/竞品/一句话想法）。输出：定位 + 目标用户 + 核心价值。
  门禁：必须含**量化 success-metrics + 反指标**（如"30 天转化率 +15%"+"退货率 ≤5%"），
  不可只有定性目标。无反指标的 PV 不放行。
- **BRO 业务角色** — 上游：PV。输出：参与业务的全部角色，每个含职责。
  门禁：角色 = **岗位/职责抽象**，**不得以人名充当**——人换岗角色不变；当前负责人作为属性括注，
  示例写法 `材料审核岗（当前负责人：王某某，财务部）`；下游 CP/UC/JF/SM/BR 的角色引用一律用角色名，
  @人 只是联系人不是角色。角色是下游权限的唯一来源，角色清单必须能回答"每个流程谁负责"。
  遗漏一个执行角色即不通过。
- **BEN 业务实体** — 上游：PV。输出：业务涉及的对象（活动/订单/券…）+ 实体关系。
  门禁：必须画出实体关系，是下游数据模型的唯一来源。
  **数据模型（字段/列名映射/主键）归 MRD（BEN 实体定义内），PRD 只引用不重复定义；
  实现层（建表 SQL/索引）归 jf-data（独立链消费 BEN）**。每个实体条目必带**层级**与**领域锚点**
  ——IA BO 汇总时直接取用，避免重推。

**BEN 实体条目两字段**：

- **层级**：聚合根 / 子 / 孙 / 交叉 / 引用五类。判定问三问——状态在谁身上流转？
  子对象挂谁下？删掉谁业务无法独立？（IA BO 聚合根判定与本字段一致，此处先标注供汇总取用）
- **领域锚点**：标注实体在客户需求清单中所属的一级领域（如「专家」归 综合管理>专家管理），
  供 IA 判断是否升为平台级共享对象

**BEN 画域内层级**：各模块 MRD 的 BEN 图彼此隔离，看不出跨模块共享/流转/同构——跨模块视角
（共享对象、流转对象、同名不同物）由 IA 的 BO 块统一梳理（BEN 负责域内层级，BO 汇总全站）。

- **CP 核心流程** — 上游：BRO + BEN。输出：业务视角端到端流程（如 创建→审核→发布→领取→核销）。
  门禁：必须覆盖**所有角色的主流程**，是业务视角不是用户视角（CP 讲"事情怎么流转"）。
  **核心流程一律画图：一条核心流程 → 画 mermaid flowchart（节点=环节动作，箭头=流转顺序），
  不用文本流程块；多条核心流程 → 先画一张「核心流程总关系图」描述流程之间关系
  （先后衔接/并行/循环），再逐条画各流程图；编号保持 CP-xx，图下可保留一句说明（含来源标注）**。
  图示布局按上文「mermaid 图示布局」执行；CP 块开头放「层级总览图」（见上「MRD 文档大纲与编号规则」）。
- **UC 业务用例** — 上游：CP。输出：每个流程节点拆成"谁做什么"的一句话用例，
  带 **UC 编号**（UC-01…）。门禁：必须是客户听得懂的业务语言，不出现技术词；
  每个 UC 可追溯到某个 CP 节点。**UC 必须串联 BRO×BEN 并画图：每个 UC 显式写明
  「谁（BRO）对什么（BEN）做什么」——带角色主语 + 对象宾语；并画一张 mermaid 串联图
  （角色、实体各一个 subgraph，UC 为中间节点：角色 → UC → 实体），可追溯回 CP 节点编号；
  缺串联或未画图不放行**。UC 描述标注所归属 JF（见「MRD 文档大纲与编号规则」）。
- **JF 用户旅程** — 上游：UC。输出：把用例拆成用户操作步骤的主路径。
  门禁：每条旅程**只写一条主路径**，分支用注释标注；区分 JF（人怎么走）与 CP（事怎么流转），
  二者不可混写。**JF 标题标注所属 CP·UC 与主导角色**（编号带父链，见「MRD 文档大纲与编号规则」），
  如 `JF-01 发起收集任务旅程（CP-01 › UC-02 ｜ 材料审核岗）`。
- **BR 业务规则** — 上游：PV + 外部约束。输出：原始层规则条目（按本文件「规则本体」schema 组织）。
  门禁：每条含完整 6 字段；标签覆盖 ≥1 个预定义主分类；来源必带；禁止出现页面/组件/UI 细节。
  **物理位置：BR 按 UC-JF 归属分散书写，写在各自 JF 旅程下方的「业务规则」小节，不设集中 BR 大块；
  规则 ID 全局连续（BR-NN），分散不影响编号，保证 SM/DR/附A 跨节引用不失效**。
- **SM 状态机** — 上游：BR（从规则中识别状态转换子集）。输出：状态定义 + 每状态含金额/权限/转换触发条件。
  门禁：SM 是**所有下游文档的唯一权威来源**，PRD 只能引用不能重定义；每个状态要素可追溯到 BR 条目ID。
  **双层制：状态图在所属 JF 内「业务状态切换」小节涌现（旅程级视图）；权威定义收口于该 SM 的主导 JF
  （状态定义/进入条件/权限/追溯表，追溯列含 UC/BR），下游 PRD 只引用该权威收口**。

## 生成顺序（参考依赖，不是状态机）

10 块不是线性流水，是两支汇流。先生成时对照此图找上游；上游没就绪别硬写下游。

```
PV ──→ (FL 归 PRD，② 的 FR 网关承担)
  │
  ↓
BRO ┐
BEN ┤──→ CP ──→ UC ──→ JF
     │      ↑
BR ──┘──→ SM
              ↑
           DR（由 BR + PV 拍板生成，决策落座）
```

- **两支**：BRO+BEN+BR 是"业务定义支"（谁/什么/什么规则）；PV 是"产品定位支"
- **CP 汇聚两支**（谁+什么+规则 → 流程）
- **DR 旁挂**：决策记录由 BR + PV 拍板生成，供下游（PRD）引用，不参与流程汇流
- **BR→SM 汇流关系不变，变的是物理位置**：上图表达的是推导依赖；落到 MRD 文档时 BR 按 UC-JF 归属分散书写（不设集中 BR 大块），SM 在所属 JF 内涌现旅程级视图、权威定义收口于主导 JF 的 SM 小节。
- **DAG 已降级**：生成顺序是参考知识、不是状态机。状态追踪用 front matter commit + todo + 人驱动门禁
