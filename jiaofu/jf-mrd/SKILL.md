# 拍① 业务事实

## 这一拍是什么

把甲方的一句模糊想法，钉成一组互相咬合、可逐块评审的**业务事实**：谁参与、对哪些对象、
做什么、流程怎么走完、受什么规则约束、有哪些状态、哪些口径已由业务方拍板。

本拍的出口产物交客户做**业务评审**——确认「逻辑对不对」。

**只管业务层。** 话题一旦滑向 UI 或实现，停下来——那是②③的事。

## 入口

**无上游**，本拍是源头。两种进入方式：

- 用户直接说（`jf-router` 判为跨拍落点在本拍）
- ③ 的评审反馈带着**业务事实类**答复回来（按对象分流——业务事实类回本拍，需求/设计类回②）

本拍与②之间的交接走**产物自己的 front-matter**（`status` / `version` / `updated` /
`requires` / `changelog`，模板见 `jf-mrd-core/SKILL.md` 的「MRD 头部 front-matter」一节），
不另立交接文件。

## 拍内步骤表

| 步骤 | 执行者 | 输入 | 输出 | 门禁 | 回退 |
|---|---|---|---|---|---|
| 1 规则整理 | `jf-mrd-core` | 用户口述 / 会议纪要 / 逐字稿 / 旧稿 | MRD 内容块 + DR | **`check_mrd.py`** | 硬失败 |
| 2 业务评审材料组装 | `jf-review-core` | MRD | 业务评审版汇报文档（评审清单里属**业务**的那 6 项） | — | — |
| 3 客户业务评审 | 人（现场） | 业务评审材料 | 答复（**会议纪要**） | — | — |
| 4 答复回流 | `jf-mrd-core` | 答复 | MRD 修订 + DR 新增 | `check_mrd.py` | 硬失败 |

**推进判据**：产物存在 ∧ 有门禁的必须过（退出码 0）。本拍**不新增判据**——它只做
「按序走 + 收退出码 + 卡住就停下问人」。

## 出口判据

1. MRD 的 **9 个内容块**齐全（PV / BRO / BEN / CP / UC / JF / BR / SM / DR）
2. `check_mrd.py` 退出码 0
3. 客户业务评审通过 → MRD 的 front-matter 写 `status: 已确认`

第 3 条是本拍的**出口 A**，也是②的入口条件。

业务评审材料是「拿给客户评审的那份」——它是组装的产物，不是新的业务事实。

## 调用契约

**正常路径**：`jf-router` 判为跨拍落点在本拍 → 本文件按上表 1→4 步调 `jf-mrd-core`
与 `jf-review-core`，逐步骤收退出码。

**独立路径**：用户显式指名 `jf-mrd-core` 时可直接调用该模块——此时它先走 `jf-router`
判跨拍，再进自己的流程。模块行为与本拍编排无关，可独立测试。

## 公共设施

跨拍路由 `jf-router`、契约 `jf-contract`、门禁 `jf-validate`——三个基建的用途统一列在
`index.md` 的「公共设施」一节，本拍不重复列。
