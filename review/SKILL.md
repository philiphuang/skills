# 阶段汇报

纯组装，不创造新内容。从各skill产出cherry pick客户关心的12项，翻译成易消化形态，按两阶段（业务评审→设计评审）组织汇报文档，收集反馈回流MRD。

核心思路：**提取显性化**（非屏蔽）——不是砍掉工程细节，而是主动挑出客户关心的、翻译成他们能看懂的形态。

## 入口纪律

**意图不清或方案不清晰时，先梳理再走流程**：
- 需求模糊、业务逻辑不清 → 调用 `grill-with-docs` 盘问梳理
- 问题太大、路径不明 → 调用 `wayfinder` 建图寻路
- 梳理清楚后，回到本 skill 走流程

**misroute scan**（首次消息时检查）：如果用户的意图指向别的 jf-* skill，建议切换再继续。

## 两阶段

```
业务评审（确认逻辑对不对）→ 设计评审（确认长什么样）→ 开发授权（结论）
```

开发授权是前两阶段的自然产出，非并列第三种文档。

## 反馈回流闭环

```
客户评审 → 反馈（疑问/否决/新增/调整）
    ↓ 复用MRD格式记录
    ↓ 四类分流
    ↓ 回流①MRD（变更唯一入口）
    ↓ MRD修订 → 下游同步 → 下次汇报反映
```

- **⑦采集反馈，①处理变更**
- 反馈记录格式复用①原始层（原话+解读+来源+状态）

## 纪律

- **纯组装**：不创造新内容，从已有产出cherry pick
- **提取非屏蔽**：挑客户关心的，主动翻译
- **每项固定形态**：流程→流程图，状态→状态图，规则→决策表…
- **两评审+一结论串行**：业务评审(逻辑层)→设计评审(+界面+架构)→开发授权(结论)
- **通过≠零反馈**：允许带待定问题，否决类必须当场解决
- **发布**：HTML→公网，MD→飞书（md2feishu）。以上载体默认可换
