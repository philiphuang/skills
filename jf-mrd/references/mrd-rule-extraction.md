# MRD 规则整理方法论

> **本文件是 wayfinding map [#35](https://github.com/philiphuang/skills-factory/issues/35) 的目的地产物（MRD 部分）。**
> 定义从众多输入到结构化业务规则（BR+SM）的整理过程，内建增量沉淀。
> 本方法论是 ① 业务建模 skill 的核心能力，定稿后回填进 `hifi-workflow.md`（jf-prd 的 references/）。
>
> 决策来源：#36 规则本体 / #37 输入采集 / #38 增量沉淀。

---

## 0. 宗旨与定位

MRD（营销需求文档）的核心功能是**规则整理**——把散乱的输入信息沉淀成结构化的业务规则，作为整个研发暗线的唯一真相来源。

本方法论回答三个问题：
- **规则是什么**（§1 本体）：两层 pipeline
- **规则怎么来**（§2 采集）：从文本提取
- **规则怎么长**（§3 沉淀）：增量合并 + 冲突治理

承接上轮「需求成长方案」宗旨：MRD 是规则的唯一真相，变更只走 MRD（自上而下）。需求不是一次过——客户多次输入（增/删/改），规则集逐步沉淀。

## 1. 规则本体：两层 pipeline

### 1.1 两层结构

规则整理采用**两层 pipeline**，每层定位不同：

| 层 | 形态 | 定位 | 去向 |
|----|------|------|------|
| **原始层** | 自然语言 + 标签 + 来源 | 采集态：保真记录客户原话/章程原条 | **进 MRD**（规则唯一真相） |
| **加工层** | Given/When/Then 决策单元 | 清洗态：结构化，客户易懂，可推导 SM | **进汇报材料**（⑦ 阶段汇报） |

**核心原则：MRD 保真，汇报清晰。** 原始层进 MRD（保留原貌可追溯），加工层进汇报（清洗成客户易懂的决策单元）。呼应上轮宗旨——MRD 确认规则原貌，汇报呈现加工后的决策结果。

### 1.2 原始层条目结构

每条原始层规则含 6 个字段（#37 采集设计）：

| 字段 | 说明 | 示例 |
|------|------|------|
| **规则ID** | 唯一标识 | BR-07 |
| **[原话]** | 客户/章程的原始陈述，保真不动 | "金额大的活动要走财务审" |
| **[解读]** | agent 对原话的结构化解读，标注为解读待确认 | "营销活动金额 > 5000 需财务审核" |
| **标签** | 预定义主分类 + 自由标签 | [金额][审批] #营销活动 |
| **来源** | 来源类型 + 具体出处（必带） | 会议 2026-08-01 / 章程§3.2 / 竞品推断 |
| **状态** | 生命周期状态（见 §3.3） | 候选 |

**[原话] 与 [解读] 分离**是关键设计：原话留痕保真，解读可被否决，两者不混淆。解决"客户说的 ≠ 客户真正要的"——原话是证据，解读是推断，用户确认后才转正。

### 1.3 标签体系（混合）

原始层的主要结构化手段：

- **预定义主分类**（覆盖源文档"金额、审批、外部边界" + 扩展）：
  - `金额` — 金额约束、阈值、计算规则
  - `审批` — 审批流、审批条件、审批人
  - `边界` — 外部系统边界、集成约束
  - `状态转换` — 状态变更规则（与 SM 强相关）
  - `权限` — 角色/操作的准入
  - `时效` — 时间约束、有效期、冷却期
- **自由标签**（整理时随手打，后期可归纳）：
  - 实体标签：`#活动` `#订单` `#券`
  - 场景标签：`#营销` `#核销` `#高频`
  - 优先级：`#P0` `#P1`

### 1.4 来源追溯（必带）

每条规则必带来源，支撑：
- **变更治理**：冲突时按来源类型作参考（章程 > 会议口述 > 竞品推断）
- **审计**：规则来龙去脉可追溯
- **置信度**：来源类型决定置信度（章程权威 / 口述可能记错 / 推断是假设）

### 1.5 BR 与 SM 的关系：交织涌现

修正源文档边5的"线性 BR→SM"。实际整理时 **BR 和 SM 交织涌现**——状态转换本身就是规则的一种（"活动过期 → 不可领取"既是规则也是状态），整理时一起冒出来。

- SM 不是 BR 的下游派生，而是 BR 的一个**特化视角**
- SM = 原始层规则中"涉及状态变更"的子集，加工成 Given/When/Then 后的聚合视图（见 §4.2）
- 边5（BR→SM）应理解为"从规则中识别出状态转换子集"，而非"先有 BR 再生成 SM"

## 2. 采集流程：规则怎么来

### 2.1 输入的两条路径

| 路径 | 来源 | 形态 |
|------|------|------|
| **主路** | imness（IM/会议妙记）/ docness（文档）/ 调研 skill | 干净结论文本 |
| **辅路** | 用户直接给的裸输入（一段话/语音转文字） | 待处理文本 |

**三类输入统一为文本**（#37）：①会议口述、②财务章程、③竞品/行业/隐性知识，都由上游 skill（imness/docness/调研）预处理成结论文本。本方法论不负责原始噪声过滤、结构化、脱敏——那是上游 skill 的事。两条路径都进同一个采集流程，差异只在"来源"标记。

### 2.2 采集流程（agent 提取 + 用户确认）

```
上游文本（任意来源）
    ↓ Step1：agent 扫描，识别"规则性陈述"
       信号词：必须 / 不允许 / 超过 / 需要审核 / 只有...才能 / 自动 / 不得超过 等
    ↓ Step2：agent 提取候选规则条目
       每条含：[原话] + [解读] + 标签 + 来源，状态=候选
    ↓ Step3：用户确认/补充/否决
       确认原话、采纳或修正解读、补标签
原始层规则条目 [状态=已确认]
```

### 2.3 采集的关键纪律

- **[原话] 不动**：采集时原话原样录入，agent 不改写。MRD 是规则唯一真相，保真是底线。
- **[解读] 标注**：agent 当场解读，明确标注为 `[解读]`，与 `[原话]` 区分。解读需用户确认才转正。
- **来源必填**：采集时必须标来源（会议日期/章程条款号/竞品推断），无来源不收录。
- **agent 不创造规则**：agent 只从文本提取，不凭空生成规则。文本里没有的，不补。

## 3. 增量沉淀：规则怎么长

### 3.1 增量合并的三种结果

新条目（已确认）进来时，agent 按**实体+属性**维度（如"活动-金额上限"）与已有规则集比对：

| 结果 | 条件 | 处理 |
|------|------|------|
| **新增** | 没有同类约束 | 追加为新条目，状态=已入MRD |
| **细化** | 有同类约束但互补（如"上限10000" + "营销类除外"） | 合并/更新原条目 |
| **疑似冲突** | 有同类约束且矛盾（如"上限10000" vs "上限5000"） | 标记，进人工裁决（§3.2） |

### 3.2 冲突检测与裁决

**检测 = agent 自动标疑似**：
- agent 按标签体系（实体+预定义主分类）找同类约束，数值/条件不同的标为"疑似冲突"
- **只标不裁**——agent 不做业务判断，把疑似冲突呈现给人工

**裁决 = 全人工**：
- 所有疑似冲突由人工裁决，agent 不自动选
- 理由：业务规则常需业务判断（"10000 还是 5000"背后是策略，不能机械裁决）
- 来源（§1.4）作为**裁决参考**（人工可看来源：章程 vs 口述），但不做自动优先级
- 裁决结果回流 MRD（呼应上轮宗旨：变更只走 MRD）

### 3.3 规则生命周期：状态流转 + 旧规则留痕

```
候选 → 已确认 → 已入MRD → 被修订 / 废止
                                ↓
                    旧规则不删，标[废止/被修订]，保留追溯
```

| 状态 | 含义 | 触发 |
|------|------|------|
| **候选** | 刚采集，待确认 | agent 提取（§2.2 Step2） |
| **已确认** | 用户确认原话/解读 | 用户确认环节（§2.2 Step3） |
| **已入MRD** | 进入 MRD 规则集，下游可引用 | 确认后入库（新增/细化结果） |
| **被修订** | 被新规则替换 | 增量合并时人工裁决采新 |
| **废止** | 不再生效 | 业务变化 |

**旧规则留痕**：修订/废止的规则不删除，标记状态，保留版本链。支撑审计（规则怎么演变）、回溯（客户问"为什么改成这样"可查）、误操作恢复。

### 3.4 增量沉淀的触发时机

- **即时**：每次采集流程（§2.2）产出已确认条目后，立即并入规则集并做冲突检测
- **非批量**：不积压到定期批量处理——增量合并的优势在于"尽早发现冲突"

## 4. 加工层与 SM 聚合（原始层 → 汇报材料）

> 本节定义原始层如何清洗成加工层（进汇报），以及 SM 如何从加工层聚合。这两块在 wayfinding 时是雾，基于 #36/#37/#38 决策推导。

### 4.1 清洗步骤：原始层 → 加工层决策单元

加工层决策单元采用 **Given/When/Then** 范式（与 AC 同构），基于**已确认的 [解读]** 清洗（不直接碰 [原话]）：

```
原始层条目（已确认的 [解读]）
    ↓ 去重：多条解读指向同一约束的，合并
    ↓ 消歧：模糊表述（"金额大的"→"金额>5000"）基于上下文精确化
    ↓ 结构化：解读 → Given/When/Then
    ↓ 关联：保留指向原始层规则ID 的追溯
加工层决策单元 [进汇报材料]
```

**清洗示例**：
```
原始层 BR-07：
  [原话] "金额大的活动要走财务审"
  [解读] "营销活动金额>5000 需财务审核"  ← 已确认
  标签 [金额][审批] #营销活动

清洗成加工层：
  Given 活动类型为"营销"
  When 创建金额 > 5000 元
  Then 需财务审核，状态置为"待审核"
  追溯：BR-07
```

**清洗纪律**：
- 只清洗**已确认**的解读，候选态不清洗
- Given/When/Then 的每个要素都要能追溯到原始层规则ID
- 清洗产物（加工层）进汇报材料，不回写 MRD——MRD 只有原始层

### 4.2 SM 聚合视图

SM 不是独立产物，而是**加工层决策单元中"涉及状态变更"子集的聚合视图**：

```
加工层全部决策单元
    ↓ 筛选：Then 子句涉及"状态变为/状态置为"的
    ↓ 聚合：以状态为节点，转换条件为边
SM 状态转换图
```

**聚合示例**（基于 §4.1 的决策单元 + 其他）：
```
状态节点：草稿 → 待审核 → 已发布 → 已结束
转换边（来自决策单元的 When）：
  草稿 --[创建金额>5000]→ 待审核
  草稿 --[创建金额≤5000]→ 已发布（直接发布）
  待审核 --[审核通过]→ 已发布
  已发布 --[到期]→ 已结束
```

**SM 的字段**（呼应源文档 SM 定义"状态定义+金额+权限+转换触发条件"）：
- 状态定义：状态名 + 业务含义
- 金额：该状态下的金额约束（来自 [金额] 类规则）
- 权限：该状态下谁能操作（来自 [权限] 类规则）
- 转换触发条件：来自 [状态转换] 类决策单元的 When

**关键**：SM 的每个要素都能追溯到加工层决策单元，进而到原始层规则ID。SM 是视图，不是新的真相来源——真相在原始层。

### 4.3 加工层与验证层 AC 的衔接

加工层 Given/When/Then 与验证层 AC（§3.1 BDD 的输入）**同构**——这是 #36 决策的重大价值：

```
MRD 原始层规则 → 加工层 Given/When/Then（进汇报）
                          ↓ 客户确认后
                   验证层 AC（Given/When/Then）→ BDD 场景
```

BR 的决策单元和 AC 天然衔接，一脉相承。整个工作流的"规则 → 验收"链路打通。

## 5. 完整 pipeline

```
═══════════════ 采集（§2）═══════════════

上游文本（imness/docness/调研skill/裸输入）
    ↓ agent 扫描识别规则性陈述
    ↓ 提取候选（原话+解读+标签+来源，状态=候选）
    ↓ 用户确认 → 状态=已确认

═══════════════ 沉淀（§3）═══════════════

已确认条目
    ↓ agent 按实体+属性比对规则集
       ├─ 新增 → 状态=已入MRD
       ├─ 细化 → 合并更新
       └─ 疑似冲突 → 人工裁决
                      ├─ 采新 → 原[被修订]，新=已入MRD
                      └─ 保留 → 新[废止]或合并

═══════════════ MRD（原始层，§1）═══════════════

原始层规则集 [唯一真相]
  规则ID / [原话] / [解读] / 标签 / 来源 / 状态
    ↓ 变更回流（多次输入重复上述，逐步沉淀）

═══════════════ 清洗（§4，汇报前）═══════════════

原始层（已确认解读）
    ↓ 去重/消歧/结构化
加工层 Given/When/Then 决策单元
    ├─ 进汇报材料（⑦ 阶段汇报）
    └─ 筛选状态变更子集 → 聚合成 SM
```
